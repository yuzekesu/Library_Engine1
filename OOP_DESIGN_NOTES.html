DirectX Rendering OOP Design Notes

Summary

The main architectural improvement is to separate responsibilities and prefer composition over inheritance. Currently, window resources, global DirectX resources, rendering threads, mesh data, GPU buffers, transforms, cameras, and pipelines are tightly connected.

Recommended improvements

1. Split DirectX11Manager into three objects

  • GraphicsDevice: owns the device, adapter, factory, and immediate context.
  • RenderSurface: owns per-window resources such as the swap chain, render target, depth target, viewport, composition objects, and resize handling.
  • CommandExecutor: handles command-list submission, but only if multithreaded rendering is genuinely needed.

DirectX11Manager currently combines all three responsibilities and uses global static state together with an isMainManager lifetime flag.

2. Remove most singletons and static global access

Pass GraphicsDevice& or a smaller rendering context explicitly to objects that require it. This makes ownership clear, avoids hidden dependencies, and makes multiple windows or devices easier to support.

3. Make interfaces actual interfaces, or rename them

IMovable and IDrawableIndexedMesh are concrete, state-owning base classes rather than interfaces.

  • Rename IMovable to Transform.
  • Split IDrawableIndexedMesh into MeshData and GpuMesh.
  • Reserve the I prefix for classes that define virtual contracts.

4. Use composition for entities

Instead of making Entity inherit from movement and mesh classes, let it contain or refer to those parts:

struct Entity {
    Transform transform;
    std::shared_ptr<Mesh> mesh;
    std::shared_ptr<Material> material;
};

An entity has a transform and a mesh; it is not itself a transform or mesh.

5. Separate CPU assets from GPU resources

Loading .im files, storing vertex/index vectors, creating Direct3D buffers, and representing a drawable object should not all be responsibilities of one class.

  • MeshData: stores vertices and indices in CPU memory.
  • GpuMesh: owns vertex and index buffers.
  • MeshLoader: parses mesh files.
  • AssetCache: optionally shares one GPU mesh between many entities.

6. Make the camera explicit

TestPipelineManager currently treats the first entity in its collection as the camera. Pass a Camera or RenderView explicitly instead. The position of an object in a collection should not determine its role.

7. Treat pipelines as render passes

A pipeline or render pass should own shaders and fixed pipeline state and should record draw commands. It should not own the scene or decide when the swap chain is presented.

A central Renderer should:

  1. Begin the frame.
  2. Clear the render and depth targets.
  3. Execute every render pass.
  4. Finish and submit the command list once.
  5. Present the completed frame once.

Currently, every pipeline can finish a command list and enqueue a presentation. This will become problematic when several rendering passes are used in one frame.

8. Introduce a small frame context

Instead of passing both IRenderWindow& and the complete DirectX11Manager& into every pipeline, pass a RenderContext& containing only what a pass needs:

  • the device context;
  • render and depth targets;
  • the viewport;
  • camera data;
  • frame timing data, when required.

9. Clarify ownership

GameManager currently uses static local shared_ptr collections to keep entities alive while most other systems store weak_ptrs. Give a Scene or World clear ownership of the entities.

  • std::unique_ptr for exclusive ownership.
  • std::shared_ptr only for genuinely shared resources.
  • std::weak_ptr only for optional, non-owning observers.

10. Simplify threading initially

The current render thread continuously checks a shared queue. For the current size of the project, rendering directly with the immediate context would likely result in a simpler and safer design.

If render threading is retained, move it into an explicit RenderExecutor with a condition variable, clear ownership, and deterministic shutdown.

11. Hide raw Direct3D binding details

Avoid APIs such as PPVertexID3D11Buffer(). Give GpuMesh a Bind(context) operation or return a small immutable buffer view. Calling code should not need pointer-to-pointer access to internal COM resources.

12. Define one matrix convention

Document and enforce the column-vector convention: matrices multiply vectors as matrix * vector. Put any transpose or memory-layout handling at one clearly defined CPU-to-shader upload boundary.

Suggested first refactor

  1. Split DirectX11Manager into device-level and window-level objects.
  2. Convert Entity from inheritance to composition.
  3. Move scene and camera ownership out of TestPipelineManager.
  4. Make Renderer responsible for frame boundaries and presenting.
